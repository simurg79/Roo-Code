# Phase 6 — Unified Gap Analysis Matrix

> Parent plan: [`00-plan.md`](00-plan.md) · Index: [`README.md`](README.md)

## A. Methodology / Reading Guide

**Question this file answers.** For every Roo-Code feature catalogued in [`10-roo-inventory.md`](10-roo-inventory.md) (and the vault patterns in [`20-roo-vault-inventory.md`](20-roo-vault-inventory.md)), what is the closest equivalent — or the explicit gap — in (i) GitHub Copilot Chat (VS Code), (ii) GitHub Copilot CLI (`@github/copilot`), and (iii) Squad layered on top of either Copilot surface?

**Severity legend (per-target cell).**

- 🔴 **blocker** — no acceptable workaround; would force keeping Roo or accepting a hard loss.
- 🟠 **major** — no first-class equivalent but a workable workaround exists with non-trivial effort.
- 🟡 **minor** — different ergonomics; functionality preserved with prompt/process changes.
- ✅ **parity** — drop-in or near-drop-in replacement.
- ➕ **additive** — Copilot/Squad ships a capability Roo does not have at all.

**Dual-severity convention.** Each row's _Gap severity_ column carries **per-path severities** when Chat and CLI diverge — written as `Chat <icon> / CLI <icon>` (e.g., `Chat 🔴 / CLI 🟠` for G-1). When both paths are equivalent, a single icon is used.

**Squad column convention** (see also § E). The Squad cell expresses **what Squad adds on top of CLI** for that row, not a separate replacement path. Values: `same as CLI` (no delta), `+ <feature>` (additive on Path C only), or `n/a` (Squad has no opinion on that surface).

**PAW column convention** (added Phase 10b — see also § G "PAW Surface Summary"). The PAW cell expresses **what PAW adds (or fails to add) on top of its host** (Copilot Chat, Copilot CLI, or Claude Code), since PAW is a prompt-and-skill bundle with no model client of its own (per [`35-paw-inventory.md` § 2.3](35-paw-inventory.md#23-key-dependencies-what-they-hint-at)). Severity is scored against **what PAW itself contributes**, not against the host. Conventions:

- `inherits <Chat|CLI>` — PAW does nothing for this row; the host's cell applies unchanged.
- `+ <feature>` — PAW _adds_ a capability the bare host doesn't have (e.g., a workflow state machine, artifact-based phase persistence, multi-model planning).
- `🔴/🟠/🟡/✅` — severity for what PAW itself does or fails to do (P-/PW- IDs from [`35-paw-inventory.md` § 12](35-paw-inventory.md#12-paw-gap-catalog-preliminary)).
- Each cell carries a 1-line evidence string and a cross-ref to the relevant `35-paw-inventory.md` section, e.g., `🟠 — no per-skill fileRegex; § 4 / P-1`.

**Backref IDs.** Cells reference the source-catalog identifiers rather than restating descriptions:

- **G-1…G-14, W-1…W-12** — Chat-side Gap Catalog from [`40-copilot-chat-research.md` § Limits / Known Gaps](40-copilot-chat-research.md#limits--known-gaps).
- **CG-1…CG-15, CW-1…CW-12** — CLI-side Gap Catalog from [`50-copilot-cli-research.md` § 13](50-copilot-cli-research.md#13-limits--known-gaps-relative-to-roo-cli-gap-catalog--phase-5b-ii-b-2).
- **P-1…P-11, PW-1…PW-5** — PAW-side preliminary Gap Catalog from [`35-paw-inventory.md` § 12](35-paw-inventory.md#12-paw-gap-catalog-preliminary).
- **Q-NNN** — open questions from [`99-open-questions.md`](99-open-questions.md).
- **`50 § 9.4`** etc. — section anchors in source files.

Rows are grouped by Roo concept area, in roughly the order of [`10-roo-inventory.md`](10-roo-inventory.md). New gaps discovered during synthesis are tagged `[NEW]` and have a corresponding Q-ID.

## G. PAW Surface Summary (added Phase 10b — 2026-04-30)

### G.1 — How PAW slots into the matrix

PAW is **not a fifth surface comparable to Chat / CLI / Squad**. It is a Markdown-and-skill bundle that ships _into_ one of three host surfaces (Copilot CLI plugin, Copilot Chat via VS Code extension, Claude Code via NPM CLI) and inherits the host's runtime, tool registry, MCP plumbing, model client, and approval substrate. Per [`35-paw-inventory.md` § 2.3](35-paw-inventory.md#23-key-dependencies-what-they-hint-at), PAW has **zero runtime dependencies** outside `vscode` (no `@github/copilot-sdk`, no `@modelcontextprotocol/sdk`, no provider SDK).

The PAW column therefore expresses a **PAW-specific delta** per row: for most rows PAW _inherits_ the host (✅ value already in the Chat/CLI cell), for some rows PAW **adds** something the host doesn't have (`+` entries — workflow state machine, artifact-based persistence, multi-model planning, mandatory automated quality gates), and for a small set PAW has its **own** gap that survives even on top of a generous host (P-1, P-2, P-4, P-9 — no per-skill `fileRegex`, no per-skill MCP allowlist, only 2 long-lived agents, deprecated project-level instructions).

### G.3 — Three headline strengths of PAW (vs the existing 4 paths)

1. **Strict serial workflow state machine closes G-4 cleanly** ([§ 3.5](35-paw-inventory.md#35-how-phases-are-sequenced--declarative-pipeline--interactive-orchestrator)). The Mandatory Transitions table + Stage Boundary Rule + `paw-transition` gate + structured-return convention (`pause_at_milestone` / `next_activity` / `session_action`) implement Roo's serial-orchestrator semantics by _prose discipline at the orchestrator agent layer_. No other path in the gap matrix ships this off-the-shelf — every other path leaves G-4 mitigation to the user's `.agent.md` body. PAW is the first thing investigated in Phases 1–9 that genuinely _replaces_ Roo's sequential-only enforcement with a documented spec.
2. **Artifact-based persistence is strictly better than every other path's session model** (B.8 row 3, B.9 row 3, B.11 rows 1/3/4). `.paw/work/<work-id>/{Spec,CodeResearch,ImplementationPlan,WorkflowContext,Docs}.md` is committed Markdown — diff-able in PRs, code-reviewable, machine-portable across clones via the `Repository Identity` proof string, resumable from any worktree. Roo's per-task globalState, Chat's profile-DB sessions, CLI's session-state JSONL, and Squad's `.squad/log/` are all worse on at least one of {portability, code-review fitness, machine-independence}.
3. **Multi-model planning + Society-of-Thought review** ([§ 9](35-paw-inventory.md#9-model--provider-support), [§ 7.2](35-paw-inventory.md#72-parallel-vs-serial)) are first-class workflow primitives, not bolt-ons. `plan_generation_models` defaults to `latest GPT, latest Gemini, latest Claude Opus` parallel-and-synthesise; SoT supports specialist→model assignments across 9 specialist personas. This is a categorically richer model-ensemble pattern than Squad's `model-selection` skill or Roo's per-mode `apiConfigId`.

### G.4 — Three headline gaps PAW does _not_ fix

1. **G-1 (`fileRegex`) survives unchanged.** PAW has no per-skill or per-agent file-edit restriction (P-1, [§ 4.2](35-paw-inventory.md#42-per-phase--per-skill-tool-restrictions)). The `paw-implement` skill enforces `git add` discipline by prose only; nothing on disk constrains which paths a skill may write. If you're hosted on Copilot CLI, the host's `preToolUse` hook still fires and provides the same demoted-🟠 mitigation — but PAW itself contributes zero. **Q-059** asks whether the `allowed-tools:` Agent-Skills standard field will eventually populate; until it does, P-1 stands.
2. **G-2 (per-mode rules folder) is _worse_ under PAW.** Project-scope `.paw/instructions/` is **deprecated** ([`extension.ts:274-309`](../../../../phased-agent-workflow/src/extension.ts:274-309)); the only PAW-owned per-work-item knob is `WorkflowContext.md`, which is not a rules folder. Vault users who depend on per-mode rules lose the same surface area as on Path A/B/Hybrid, _plus_ lose PAW's only project-level customisation surface. Workaround is the same — inline rules into the agent body or rely on host-native `copilot-instructions.md` / `AGENTS.md`.
3. **No webview / mode CRUD UI of PAW's own** (P-6, [§ 8](35-paw-inventory.md#8-ui--surface)). PAW's VS Code extension surfaces 3 Command Palette entries + 1 Language Model Tool. Anyone migrating from Roo's `ModesView.tsx` to PAW will feel the same UX loss as on Path B/C, with no PAW-specific recovery (Path D remains the only path that restores visual mode CRUD).
